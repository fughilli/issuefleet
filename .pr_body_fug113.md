## What & why

Sometimes you want to grab a feature branch a worker is mid-flight on, make a
few quick edits in a local agent session, and hand it back — but a running
worker force-pushes its branch and commits underneath you, so today that means
either racing it or stopping it (which drops the claim and, for a poll-claimed
issue, gets re-claimed into a fresh session that loses your context).

FUG-113 adds a **release / adopt** mechanism, driven from the dashboard, so
this is a first-class move.

## The model: a new `released` phase

A released worker keeps its registry entry (the claim is **held** — no other
worker takes the issue) but its container is stopped and worktree removed, so
the branch is free to check out and edit anywhere. The daemon leaves a released
worker completely alone: it won't restart it, service it, or re-claim it. The
agent's Claude session id and turn count are remembered so a later adopt
*resumes the same conversation* rather than starting cold.

## Three dashboard actions

All are `POST`-only, confirm-gated, and go through the reconcile loop exactly
like Stop/Reset — the web thread only enqueues; the single tick thread does all
git/registry/tmux mutation, so nothing races the loop.

- **Release** (`/worker/<KEY>/release`) — stop the container, remove the
  worktree, hold the claim in phase `released`. Branch + archived transcript
  kept.
- **Adopt** (`/worker/<KEY>/adopt`, shown on a released worker) — rebuild the
  worktree from the kept branch, **fast-forward it onto origin** (picking up
  anything you pushed), re-provision preserving the session (`--resume`, not a
  new session), restart the container, and drop a re-orientation note for the
  agent.
- **Adopt a branch** (`/adopt`) — same, for a branch that never had a worker
  (built entirely outside issuefleet in an interactive session). Name the
  project, the Linear issue to attach it to, and the branch (local to the
  daemon's clone, or on the remote as `origin/<branch>`); a fresh worker adopts
  it as-is and continues from what's on it.

## Notable implementation details

- `gitops.create_worktree` gains an `origin/<branch>` fallback: a branch that
  exists only on the remote is checked out tracking origin, not silently
  re-cut from the base (which would discard the operator's work). Normal claims
  are unaffected (a genuinely new branch has no `origin/<branch>`).
- Adopted workers are exempt from the poll-claim un-claim rule (`claim_origin
  != "poll"` → only closure winds them down), so an adopted branch can ride on
  an unlabeled issue without being immediately reclaimed.
- Released workers are skipped in `_service` *before* the worktree-gone drop,
  but still honor an explicit un-claim so a closed/unlabeled issue drops the
  stale record instead of lingering forever.
- `worker.provision` learned optional `session_uuid` / `turns_taken` / `phase`
  seeds so the rebuilt worktree carries the released worker's own session
  (defaults reproduce the original fresh-claim behaviour).
- `diagnose()` and the index/worker pages get a `released` case and the new
  buttons; the daemon logs held released workers at startup.
